# Administrative Intelligence Workspace

A reusable AI workspace for running a business's admin work: chat grounded in the business's own data, an assistant (Manny), a shared calendar, a daily Pulse, and a shared brain with role-based access. One core, one profile per client. See `PLAN.md` for the roadmap.

## Profiles (one workspace, many clients)

Each client is a folder in `profiles/` with a `profile.ts`: name, short name, sidebar label, tagline, logo (an image or up to three letters), light and dark colors, roles (`roles.ts`), quick starts (`starters.ts`), area names, and which sidebar tools and pages show. Pick one in `.env.local` and restart:

```
WORKSPACE_PROFILE=construction   # or macs (the default)
```

Roles fill six fixed slots that carry the access rules in `lib/access.ts`. In the construction profile: Preconstruction Director (the "principal" slot: sees everything, approves, manages the team), Estimator ("finance": pricing and budget), Project Manager and Project Coordinator (project records), and Development (pricing and budget, decision level). The construction sidebar shows the shared brain, **Business pulse**, **Calendar**, and **Bid leveling**; the school tools and school sections are off, and the floating calendar helper is the **Scheduler** instead of Manny. The Pulse leads with bid coverage, leveling progress, estimate vs budget (under budget is on track, 0-3% over is Watch, more than 3% over is Act now), and decisions, RFIs, and risks. The calendar carries bid dates, addenda, meetings, milestones, proposal validity, RFI and decision dates, a weekly precon meeting, and a biweekly Development cost review. Both are built on the server and cut to the person's role, so pricing never reaches the browser of someone who can't see it. The construction chat works from a sample portfolio (`lib/construction/portfolio.ts`): four invented Florida projects (garden-style at DD, a wrap at Permit bidding, a podium at GMP buyout, and an industrial building at SD) with estimates against budget, bid coverage, addenda, RFIs, a VE log, decisions, and risks. Each role sees only its areas: the Coordinator and PM see no pricing, for example. Its prompt carries the leveling rules from `docs/construction/leveling-spec.md`. Each profile keeps its own shared data file (`data/shared-construction.json`), so switching profiles never mixes the two.

## Bid leveling (construction profile)

Open **http://127.0.0.1:3000/leveling** while the app is running. Drop in one trade's proposals (PDF, .txt, .eml, or a pasted email), or click **Try the sample proposals**. You get bidder cards (headline, normalized, tie-out, status), the A-I leveling package, the bid form, each proposal's record, and the BuildingConnected plug table as a CSV for Excel. Proposals are read on your computer; nothing is sent to an AI model or saved. Reading PDFs needs Poppler's `pdftotext` (Mac: `brew install poppler`).

The **Clarification emails** tab drafts one email per bidder that has gaps, asking only about that bidder's own gaps, grouped into scope, price and math, drawings, and terms, with a reply-by date (2 business days by default) and a request for a revised total. Bidders with nothing to clarify get no email. Copy the draft into Outlook and send it yourself, then click **I sent it** so the team (and the Pulse) can see what's out; **Answer is in** when they reply. Nothing is sent from the workspace and nothing is marked sent for you.

The rules are in `docs/construction/leveling-spec.md`; the code is in `lib/construction/`. `npm test` runs the leveling tests; `npm run level -- "09: Drywall" <files...>` does the same from Terminal.

## MACS Workspace (first client)

A Claude-style chat workspace for the leadership team at Micanopy Area Cooperative School (MACS): Director/Principal, Dean of Students, ESE Coordinator, Finance Officer, and Board members. Ask questions about enrollment, FAST results, FTE surveys, ESE timelines, finances, facilities, and governance. Answers are grounded in a built-in MACS dataset and generated by models routed through OpenRouter.

> **All school data in this app is sample data.** Every number, date, roster entry, and status in `lib/macs-data.ts` is illustrative. None of it comes from MACS, ACPS, or FLDOE records. The UI labels it as sample data in the header, under the composer, and in every data-backed answer. Replace it with real exports before anyone relies on it.

## Quick start

```bash
npm install
cp .env.example .env.local   # then paste your OpenRouter key into OPENROUTER_API_KEY
npm run dev                  # http://localhost:3000
```

Without a key, the app still runs in **demo mode**. Replies are assembled locally from the sample dataset, so you can click through streaming, tables, and chat management before connecting a model. A "Demo mode" pill in the header tells you which mode you are in.

| Variable | Required | Purpose |
|---|---|---|
| `OPENROUTER_API_KEY` | For live answers | Server-side only; never sent to the browser |
| `OPENROUTER_SITE_URL` | No | HTTP-Referer for OpenRouter app attribution |
| `OPENROUTER_BASE_URL` | No | OpenRouter-compatible proxy or local mock |

## Design

The UI copies claude.ai's light theme (with its dark theme as an option). Colors, spacing, type sizes, and animation timings were measured from claude.ai on 2026-10-14 and are listed in `app/globals.css`. Two deliberate differences: the branding is MACS's own, and the fonts are open substitutes (system UI sans, Source Serif 4) because Anthropic's typefaces are licensed.

Branding uses the MACS Manatees badge (`public/brand/macs-manatees.png`, also `app/icon.png` for the browser tab) with its navy `#324C9A` and gold `#D8B820` as the accent colors. The badge on file is 118×118px; drop a higher-resolution square PNG at the same paths for sharper rendering on large or retina displays.

## School sections

The sidebar lists 14 Micanopy Area Cooperative School sections that match the macschool.us menu and homepage tiles: About MACS, Enrollment, Academics, Student Life, Community, Support, Parents, Calendar, Nutrition, Donations, Employment, After School, Upcoming Events, and Manatee Spotlight. Each opens a page with a summary, key facts, links back to the live site, a "Website check" note listing gaps or conflicts found on the site, and suggested questions.

This content is real public information, not sample data. It lives in `lib/school-sections.json` (summarized from macschool.us on 2026-10-14) and is included in every system prompt; chats started from a section also get that section's full detail. It goes stale: re-check the site and refresh the JSON each term. Student names are deliberately left out.

## What's in it

- **Chats**: create, rename inline (sidebar double-click, menu, or header title), pin, archive, delete, and search. The sidebar groups chats as Pinned, Today, Previous 7 Days, Previous 30 Days, Older, and Archived.
- **Replies**: streamed word by word with a blinking cursor. Markdown renders tables, lists, callout blockquotes, and code blocks with a copy button. Each reply has Copy, Regenerate (latest reply), Fork to new chat, and Stop while streaming.
- **Roles**: the switcher (sidebar footer) changes the assistant's lens for Director, Dean, ESE Coordinator, Finance Officer, or Board member.
- **Quick starts**: Board compliance & financial summary, FAST PM1 growth gaps, FTE Survey 2 audit readiness, and a ParentSquare newsletter draft from faculty notes.
- **Settings**: custom instructions appended to the system prompt, theme (light/dark/system), and delete-all.
- **Persistence**: chats, active chat, model, role, theme, and custom instructions live in this browser's `localStorage`. Nothing is stored on a server.

## Shared workspace (one brain for the team)

The workspace is shared: staff sign in with their own name and passcode, and everyone sees the same decisions, Claims and Supplies sheets, onboarding, shared brain, and activity feed. Chats stay in each person's browser.

- **Accounts and roles.** The Director creates the first account with `MACS_SETUP_CODE`, then adds staff on the Brain page's Team tab. Roles decide what each person sees, and the server enforces it on every shared read and write and on what the chat is given: the front office never sees finance, and Finance never sees IEPs. Passcodes are stored as scrypt hashes; sessions live on the server and end when an account is turned off or its passcode is reset.
- **Every fact has a source.** Brain facts say whether they came from the website, a staff member, an agent, or sample data, and who added and approved them.
- **Agents propose, people approve.** Mac ends a reply with "Suggest for the brain: ..." when you tell it something lasting; the workspace files it as a proposal. The Director (or Finance, for finance facts) approves it before it reaches every chat.
- **One activity feed.** Staff and agents write to the same feed ("Mac for Dana drafted a reply on Reimbursements"), filtered by role.
- **Storage.** Accounts in `data/accounts.json`, shared data in `data/shared.json` (or `MACS_DATA_DIR`). Back that folder up.
- **No passcode on your own computer.** Set `MACS_NO_SIGNIN=1` in `.env.local` and run `npm run dev -- -H 127.0.0.1`: opening the app from that computer signs you in as the Director (`MACS_LOCAL_NAME` sets the name). Requests from any other device still need a passcode, and `npm run start:server` refuses to start with it on.

### Running it on the school's VPS (with Bops and Orgo)

Bops' own README says its server trusts every request it gets and must not be exposed to the internet, and it uses Tailscale for private access. Run MACS the same way:

```bash
npm ci && npm run build
# .env.local: OPENROUTER_API_KEY, MACS_SETUP_CODE (long), optionally MACS_DATA_DIR
npm run start:server            # refuses to start with no accounts and no MACS_SETUP_CODE; listens on 127.0.0.1:3000 only
tailscale serve --bg 3000       # HTTPS on the school's tailnet; only signed-in tailnet devices can reach it
```

Don't open port 3000 (or the Bops port, 3210) to the internet. Put staff devices on the tailnet, then share the `https://<server>.<tailnet>.ts.net` address. Cookies are marked Secure over HTTPS.

## Before using real school data

1. **Student privacy.** Everything in the dataset is sent to OpenRouter and the chosen model provider on every request. Confirm MACS/ACPS data-sharing policy and FERPA obligations before loading real records. Keep students de-identified, as the sample's `S-####` codes do.
2. **Data in the page code.** Sign-in now guards every API, the chat, and the shared store, but the sample dataset and roster are still built into the page code, so they reach a browser before sign-in. Real records must be served from the server after sign-in instead.
3. **Unverified details.** The curriculum list, bell times, assessment windows, survey dates, and statute references came from the project brief or general Florida practice. They have not been checked against macschool.us, ACPS, or current FLDOE guidance.
